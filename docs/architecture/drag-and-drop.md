# Drag and drop

- **Drag and drop** (`map/MapDrops.kt`, `home/HomeDrops.kt`, `data/Dropped.kt`, `map/IdeaDrag.kt`):
  - **Onto a map:** the map's WebView has a drag listener (`MapDropListener`), ahead of the page's own, which only takes text into an idea being typed.
    The page lights up the idea under the finger with Orbit's `getNodeAt` and `setDropTarget`, as its own drags light theirs (`dropOver`, `dropTarget`), and says where a drop lands (`dropAt`).
  - **What a drop adds** goes through what pasting uses (`paste`), or, for several pictures and videos, `addNodes`: one change, one Undo.
  - **Home** takes map files and text through Compose's `dragAndDropTarget`.
    Compose hands a drop to the last target a drag was over, which a quick drag can leave on the list as it goes on to a map beside it, so the list lights up by where the drag is, and takes only a drop let go over it.
  - **Files of other kinds,** a PDF or a spreadsheet, join the idea's files (`DropPlan.Files`), with every file let go with them, copied in as they are and added with one Undo.
  - **Files** are read with the permissions the drag lends the activity (`requestDragAndDropPermissions`), held until they're in, and only from other apps' content addresses (`importable`), as imports are.
    Whatever the other app's provider throws back, or Android lending its files, fails only the file it was about, with the app's usual message (`fromProvider` in `data/Dropped.kt`, and the importer's own catches): a permission taken back, one it can't lend, an address it no longer knows, a broken cursor.
    A text file is read whole, up to a map's text on the list of maps (`MAP_TEXT_LIMIT`) and a list's on a map, and decoded at once, so it's never cut, nor its encoding told from part of it (`readTextFile`).
  - **Several files** that are other versions of maps here are asked about one after another, as one is (`OtherVersions` in `OrbitApp.kt`, through `ImportResult.SeveralFiles`), the private ones behind the screen lock as ever, and what the rest brought is said once they're answered.
  - **A question outlives Orbit's process.**
    Each file waiting for an answer is kept where its zip was unpacked, `unpacking/<id>/` in Orbit's own files, which neither backups nor other apps reach: its text and what it says of itself in `.arrival.json`, beside its files (`WaitingArrivals`).
    The screen's saved state says only which, in order, whether each opens its map, and how many were answered (`Arrivals`), nothing of the maps, so the screens Android brings back after stopping Orbit, as it may while the screen lock is asked for, ask them again as they were, a private map's as privately: only once the maps are read, which says which are private, and a question about a map Orbit has no details of keeps which it is to itself while private maps are locked, and Recents out (`arrivalHides`, `arrivalNamesPrivate`).
    Each goes once answered Neither, or as a screen starts anew, which asks none of them; a start's cleaning of leftovers keeps them a week (`WAITING_LEFTOVER`), and other unpacked zips an hour.
  - **An answer outlives Orbit's process too.**
    Update or Keep both is kept beside the arrival's files, in `.arrival.json`, with when it was answered, before the screen's saved state stops listing the question (`Arrivals.answer`, `WaitingArrivals.accept`), and the app takes it in, not the screen (`Intake`, in the app's scope, one at a time in the order answered), so neither a screen made again nor one that closes stops it; its files go only once it's in.
    Those Orbit stopped before they were in are taken in as Orbit starts again, in the order they were answered, once the maps are read (`Intake.resume`), without opening their maps; neither a new screen nor the cleaning of leftovers lets an answered one go (`WaitingArrivals.isAnswered`).
    It's taken in once however often that runs (`MapBundles.receive`): Update writes only over the text it was answered for (`base`, its hash), which is the map's own, or the one the Updates answered for the same map before it give it (`Intake.coming`), or one that's the arrival's already, whose history then gets no second version; a map it adds keeps the arrival's own identity when no map here has it, as when the map it was another version of went meanwhile, kept with the answer before the map is added (`WaitingArrivals.addsAs`), and otherwise takes one chosen with the answer (`copy`); Keep both's map is made in the arrival's own folder (`.copy`), where a start's cleaning of leftovers never deletes the files moved into it, before it takes its place among the maps in one step.
    An arrival's files are wherever it left them: its folder, its `.copy`, or, moved by an Update that stopped, the map it updates (`WaitingArrivals.whereIs`).
    One that can't be taken in, as on a full storage, or whose map changed since it was answered (`ChangedSinceAnsweredException`), waits again with its files, marked to be asked again (`ask`): why is said, under "Couldn't take that map in" (`Arrivals.notTakenIn`), then the question comes back, and every screen that starts asks it until it's answered.
    So does one whose answer can't be kept beside it, as on a full storage, rather than be taken in with nothing on disk to finish it; and an Update answered for the text of one before it that couldn't be taken in is for the text that one was for, which the map still has (`Intake.notIn`), not one whose map changed.
    Earlier versions read an answered one as one waiting for an answer, and let it go as a new screen starts.
  - **Files opened with Orbit and things shared to it** go through the app too: a request waits for a screen to take it, even one that came before the screens were up or as one was made again, and is taken once (`Intake.request`); a file or text to import is imported in the app's scope, and what it brought waits for the screen there is then (`Intake.outcomes`).
    Each import is kept on disk from before it starts until a screen takes what it brought (`requests/<id>.json` in Orbit's own files, `ImportRequests`), and the screen's saved state lists the ones it waits for, so the screen Android brings back after stopping Orbit imports again one it stopped in the middle of, with the file's permission that screen still holds, or opens the map one made, never both (`Intake.resumeImports`); a new screen, whose task was closed and the permissions with it, lets them go.
    Another version of a map here that one brought is kept for every screen to ask about (`WaitingArrivals.keep`, `ask`), so it's asked even when Orbit stopped before any screen did.
    Each map an import makes is kept in its record as soon as it's there (`ImportProgress`), so one run again makes only the rest: a new map for shared files gets its files copied into it again, unless they're in already, and one that went to the trash, its files not put on it, is no longer counted (`unmaking`), so a run again makes another rather than use it; a workbook's sheets, which come in together (`MapRepository.addAll`), are kept in the record together and never made again; only an import stopped in the instant between maps being written and its record saying so makes them twice.
    Earlier versions never read the records.
    Files and text shared to the map that's open wait for its page to be ready, however soon they came, and go with the map if it closes first (`PendingShares`, `MapViewModel.takeShares`): the map's screen takes what waits each time something's offered (`PendingShares.offers`), so one offered as another is taken, or like it, is never missed.
  - **Out of Orbit:** an idea lifted on the map and dragged out of the window (`dragOut`) becomes a system drag:
    Android's `startDragAndDrop`, from the page's view, with a synthetic cancel so the page lets go of the press.
    Rows of the outline start one too.
    Its text is the idea's outline (`ideaOutline`, the same as `outline` in web/bridge.ts, which copying gives), nested up to `OUTLINE_DEEPEST` levels, deeper ideas listed at that depth: a branch thousands of ideas deep is text about the size of its names, not of its depth squared.
  - **Back in:** an idea of the map dropped on it moves.
    Android gives a drag's local state only to the window it started in, and the outline's sheet is a window of its own, so the idea's map and id also travel in the drag's item, with a flag in its description saying it's one of Orbit's.
  - **Behind a private map's lock** the page takes part in no drag.
    A map that locks while open stays under the lock's cover (`PrivateMapGate`), and its page is made invisible there, which Android leaves out of drags altogether: neither the map nor a field typed into takes a drop, and nothing lights up.
    An idea on its way out is called back with `cancelDragAndDrop` from the window it started in.
    One from the outline's sheet on a phone outlives the sheet, which steps aside as the drag starts, so that one goes on.
    A file with another version of a locked private map asks for the screen lock before it updates it.
